# 烧录与编程指南

本文档说明如何把 **固件** 和 **音色库** 烧进 RP2350 音源板，重点解决一个容易踩坑的
问题：**板上有 4 片 Flash，但 RP2350 的 bootrom 只认其中 1 片。**

---

## 1. 先搞清楚：4 片 Flash 里谁能被 bootrom 看到

| Flash | 片选 | 挂在哪 | bootrom 能直接烧吗 |
|---|---|---|---|
| **U1 启动盘** 4MB (W25Q32) | **CS0**（专用引脚） | QMI M0 窗口，0x10000000 | ✅ **能**，这就是标准 UF2 烧录路径 |
| **U2 数据盘1** 16MB (W25Q128) | **CS1** = GPIO19 | QMI M1 窗口，0x11000000 | ⚠️ **有条件**，取决于 OTP 配置 + 勘误 E14 |
| **U3 数据盘2** 16MB (W25Q128) | CS2 = GPIO8 | 软件片选 | ❌ **不能**，bootrom 完全不知道它存在 |
| **U4 数据盘3** 16MB (W25Q128) | CS3 = GPIO9 | 软件片选 | ❌ **不能** |

**结论：U3/U4 必须靠我们自己的固件来烧。** 这不是可以绕过的限制，
因为 bootrom 里根本没有访问 CS2/CS3 的代码路径。

> 关于 U2：bootrom 通过 OTP `FLASH_DEVINFO.CS1_SIZE` / `CS1_GPIO` 知道第二片的存在，
> 文档里写着它「会在进入 flash 启动路径或 BOOTSEL 模式时自动配置这个 GPIO」。
> **但勘误 E14 说：CS1 挂在非 GPIO 0 的引脚上时，bootrom 会配错 pad。**
> 我们用 GPIO19，所以**不能依赖 bootrom**。

---

## 2. 推荐路线：U2/U3/U4 全部由固件负责烧

因为勘误 E14，最稳的做法是**不碰 OTP**，把三片数据盘**全部**交给固件管理。
这样 U2 和 U3/U4 走同一条代码路径，行为一致、可预测。

### 2.1 固件里的两种工作模式

固件启动时判断应该进哪个模式：

```
上电
 │
 ├─ 检测到 BOOTSEL 按键按住  ──► 模式 A：USB 大容量存储（刷固件本身）
 │                                出现在电脑上是一个 U 盘
 │
 ├─ 检测到音色库分区头无效    ──► 模式 B：音色库刷写模式
 │  或长按 BTN1 3 秒             通过 USB CDC 接收数据，逐个烧 3 片数据盘
 │                                数码管显示进度：`00` → `99` → `--`(完成)
 │
 └─ 否则                      ──► 正常播放模式
```

数码管只有 2 位，所以进度就用两位数字，够用了。

### 2.2 模式 A：刷固件（用标准 UF2）

这是最常规的路径，和普通 Pico 2 完全一样：

```bash
# 1. 按住 BOOTSEL 键，插 USB（或插着 USB 按一下 RESET）
#    电脑上出现一个名为 RPI-RP2 的 U 盘

# 2. 把 .uf2 拖进去，或者用 picotool
picotool load -v -x build/gmss_synth.uf2
```

或者纯离线方式：把 `build/gmss_synth.uf2` 文件直接拖到 `RPI-RP2` 盘符，
板子会自动重启并运行。

**生成 UF2 的命令**（pico-sdk 工程构建时会自动做）：

```bash
picotool uf2 convert build/gmss_synth.elf build/gmss_synth.uf2 \
    --family rp2350-arm-s
```

> RP2350 有两个家族 ID：`rp2350-arm-s`（Arm 核）和 `rp2350-riscv`（RISC-V 核）。
> 我们用 Arm，所以是 `rp2350-arm-s`。**家族 ID 写错的话 UF2 会被 bootrom 拒绝**
> （表现为拖进去没反应，或者提示"文件不是有效的 UF2"）。

### 2.3 模式 B：刷音色库（自定义协议）

因为我们做不出"拖一个文件就自动分片"的效果（bootrom 不支持），
所以用一个 **USB CDC 虚拟串口 + 简单协议**，PC 端工具负责分片。

**为什么不用 USB MSC（大容量存储）**：MSC 要 FAT 文件系统，代码量大且容易出 bug。
CDC 协议只要几十行，而且我们的 PC 端 Python 工具本来就要生成二进制镜像，
顺手发送即可。

**协议格式**（极简，方便调试）：

| 方向 | 字节 | 含义 |
|---|---|---|
| PC→板 | `0xA5 'E' <chip> <addr:u32le>` | 擦除 chip 从 addr 开始的 4KB 块 |
| PC→板 | `0xA5 'W' <chip> <addr:u32le> <len:u16le>` | 写数据，随后跟 len 字节 |
| PC→板 | `0xA5 'V' <chip>` | 校验（读回 CRC32 比对） |
| PC→板 | `0xA5 'D'` | 完成，重启进播放模式 |
| 板→PC | `0x5A <status>` | 0=OK，1=擦除失败，2=写失败，3=校验错，4=参数错 |
| 板→PC | `0x5A 'P' <pct>` | 进度 0~100 |

**PC 端用法**：

```bash
# 生成镜像（4 个文件：boot.bin / chip0.bin / chip1.bin / chip2.bin）
python -m gmss.build soundfont.sf2 --out build/font/

# 烧录（自动识别 /dev/ttyACM* 或 COM*）
python -m gmss.flash --port COM7 --erase --verify build/font/
```

烧 48MB 大约需要 **60~90 秒**（USB 全速 12Mbps，实际有效约 8Mbps）。

## 3. 备选路线：SWD + 调试器

如果你有调试器（树莓派 Debug Probe、J-Link、CMSIS-DAP 等），可以用 SWD 直接烧：

```bash
# 刷固件到 CS0
openocd -f interface/cmsis-dap.cfg -f target/rp2350.cfg \
        -c "program build/gmss_synth.elf verify reset exit"
```

**但 SWD 也烧不了 U3/U4**——因为 swboot/BOOTROM 的 flash 访问路径同样只覆盖 CS0（和可选的 CS1）。
SWD 的价值在于：**当固件刷坏了、USB 也进不去时，可以救砖**。

> **救砖技巧**：RP2350 上电时会先看 QSPI CS 脚是否被拉低（BOOTSEL），
> 如果没有有效固件且 USB 也没接，它会停在 bootrom 里等。
> 实在不行用 `picotool reboot -f -u` 强制进 BOOTSEL。

## 4. 出厂方案：先烧片子再焊板

如果你要做小批量（比如 10 台以上），最省事的其实是**在焊接前用编程器烧裸片**：

1. 用 SOP-8 测试座 + CH341A / Dediprog / RT809 等编程器
2. 把 4 个镜像文件分别烧进 4 片 Flash
3. 再上 SMT 贴片

**优点**：产线不用管固件逻辑，一次成型。
**缺点**：改音色库要拆机重烧。

所以推荐**两者都留**：出厂用编程器，售后/更新用模式 B。

## 5. 开发环境搭建（从零开始）

```bash
# 1. 工具链
#    Windows 推荐用 Raspberry Pi Pico 官方安装器，或手动装：
#    - arm-none-eabi-gcc  (ARM 工具链)
#    - cmake, ninja
#    - python3
#    - picotool
#    - git

# 2. pico-sdk
git clone --recurse-submodules https://github.com/raspberrypi/pico-sdk.git
export PICO_SDK_PATH=/path/to/pico-sdk
# Windows: setx PICO_SDK_PATH "C:\path\to\pico-sdk"

# 3. 构建
cd firmware
mkdir build && cd build
cmake .. -G Ninja -DPICO_BOARD=pico2 -DCMAKE_BUILD_TYPE=Release
ninja
```

> **`-DPICO_BOARD=pico2` 很关键**：它告诉 SDK 目标是 RP2350 而不是 RP2040。
> 写错会导致链接脚本用错地址映射（还记得 RP2350 的 SRAM 布局和 RP2040 完全不同吗）。

## 6. 常见问题

| 症状 | 原因 | 处理 |
|---|---|---|
| 插 USB 电脑没反应 | **USB-C 的 CC1/CC2 没接 5.1kΩ 下拉** | 补上，这是 Type-C 做受电端的硬要求 |
| 拖 UF2 进去没反应 | 家族 ID 不对 | 用 `--family rp2350-arm-s` 重新生成 |
| 固件能跑，音色库读不到 | U2 的 pad 没配对（勘误 E14） | 固件里显式配置 GPIO19 为 F9、开输入缓冲、关内部上下拉 |
| 音色库读出来全是 0xFF | **QE 位没置**，四线模式没开 | 初始化时写状态寄存器 2 的 QE 位 |
| 音色库读出来全错乱 | `0xEB` 命令的地址/dummy 周期数不对 | 检查 dummy cycles 设置（W25Q128JV 用 0xEB 需要 6 个 dummy cycle） |
| 只有前 16MB 能读 | 第 2、3 片的片选逻辑没生效 | 软件片选要用普通 GPIO 输出，不要配成 F9 |
| 播一会儿静音 | **I2S 时钟停了超过 4 个 LRCK 周期** | PCM5102A 会重新初始化并静音；检查 DMA 是否欠载 |
| 声音有周期性咔哒 | ADPCM 关键帧定位算错，或循环点不在整数周期 | 见转换工具 README 的"踩过的坑" |

## 7. 一份可执行的最小验证清单

打板回来之后，**按这个顺序验证**，每一步都能独立定位问题：

- [ ] **1. 3.3V 和 5V 电压正常**（万用表量，不要直接插 MIDI）
- [ ] **2. USB 能被识别**，`RPI-RP2` 盘出现 → 说明 USB-C 的 CC 下拉、D+/D- 都对
- [ ] **3. 点亮 LED**：烧一个最简单的 blink → 说明基本系统 OK
- [ ] **4. 读 Flash ID**：读 CS0 和 CS1 的 JEDEC ID，都应是 `EF 40 18`
      → 说明 QSPI 总线和 CS1 的 pad 配置都对
- [ ] **5. I2S 出声**：播放 1kHz 正弦，示波器量 BCK=3.072MHz、LRCK=48kHz
      → 说明 PIO 分频算对了
- [ ] **6. 听感验证**：耳机插模块，听正弦是否干净、有无咔哒
- [ ] **7. MIDI 环回**：接键盘，数码管显示音符号 → 说明光耦和 UART 都对
- [ ] **8. 读数据盘**：从 U2/U3/U4 各读一段，比对 CRC → 说明三片都能用
- [ ] **9. 复音压力测试**：同时按 20 个音，听有无爆音 → 验证 CPU 余量

**关键：第 4 步是分水岭。** 如果 CS1 读不到 ID，不要往下做——
先解决 pad 配置问题，否则后面所有数据盘的代码都是白写。

## 8. 关于 OTP：什么时候才需要动它

**默认建议：完全不碰 OTP。**

OTP 是**一次性可编程**的，烧错了芯片就废了。我们的设计**不需要**它，
因为固件自己就能配置 CS1 的 pad 和 QMI 寄存器。

只有在下面这种情况才考虑烧 OTP：

- 你希望 **BOOTSEL 模式下 bootrom 也能访问 U2**
  （例如想用 UF2 直接烧 U2 而不用自定义协议）

那时需要：
```
FLASH_DEVINFO.CS1_GPIO  = 19
FLASH_DEVINFO.CS1_SIZE  = 12   (4KiB << 12 = 16MiB)
```

> ⚠️ **勘误 E14 就卡在这里**：bootrom 在 CS1 挂非 GPIO0 时会配错 pad。
> 所以即使烧了 OTP，U2 的访问也**不一定**可靠。
> **建议先用 `picotool otp get` 之类的只读命令确认现状，不要急着写。**
> 如果非要写，务必先在一块单独的芯片上验证。

因为存在这个不确定性，本设计的固件**按"bootrom 不知道 U2"来写**，
自己完整管理三片数据盘。这样无论 E14 影响如何都能工作。
